## تنظیمات و سلامت

- `PULSE_ENABLED=true` و `COMPOSE_PROFILES=pulse` در تنظیمات خصوصی سرور ثبت شدند. کلید تصادفی `PULSE_SECRET_KEY` برای API و worker یکسان است؛ نسخهٔ محدود به مالک فایل روی سرور و نسخهٔ DPAPI بیرونی نگه داشته شد. هیچ مقداری در Git یا این گزارش نیست.
- `.env` تاریخی سرور `APP_ENV=preview` داشت و API از overlay حالت Production می‌گرفت. برای worker نیز override صریح `APP_ENV=production` اضافه شد. سایر مقادیر قبلی محیط حفظ شدند؛ هیچ seed اجرا نشد.
- API، وب، gate و DB سالم؛ worker در حال اجرا با restart صفر، قفل advisory فعال و بدون خطای تکراری است. worker طبق طراحی PR healthcheck HTTP ندارد.
- سلامت API: `status=ok`، `db=ok`، نسخه و SHA مطابق بالا. `/login` پاسخ ۲۰۰، API بدون نشست پاسخ ۴۰۱؛ دسترسی خروجی سرور به `https://b2b.isaco.ir` پاسخ ۲۰۰ داد. فایروال تغییر نکرد.
- هر چهار جدول `pulse_connections`، `pulse_commands`، `pulse_runs` و `receptions` خالی بودند. اطلاعات ورود کسب‌وکار وارد نشد و فرمان «شروع»، آزمایش اتصال یا خواندن صادر نشد.
- gate موجود حفظ شد؛ اصلاح محلی آن دقیقاً از قبل در main بود. Source by HEDAX، DNS و دسترسی کارکنان تغییر نکردند.

## رخداد نصب و بازگشت

تلاش اول پس از migration و سالم‌شدن API/وب به علت فرمان نصب متوقف شد: `docker compose up --wait` برای worker فاقد healthcheck خطا داد، با اینکه worker بالا آمده و قفل را گرفته بود. این خطای orchestration بود. سرویس‌ها متوقف شدند، پایگاه از پشتیبان نهاییِ تأییدشده بازگردانده شد، تصاویر و تنظیمات قبلی برگشتند و سلامت v1.0.10 تأیید شد. پایگاه تلاش ناموفق نگه داشته شد؛ تعداد رویداد ممیزی کاربری در پنجرهٔ آن تلاش **صفر** بود.

پس از اصلاح فرمان، API/وب با `--wait` و worker جداگانه بدون `--wait` بالا آمدند؛ سلامت worker با فرایند، قفل و لاگ کنترل شد. نصب دوم با پشتیبان تازه و همان artifact بدون تغییر کد موفق شد؛ سپس شمارهٔ v1.0.11 ثبت شد.

## آزمون و محدودیت بررسی زنده

CI همان main: shared **۱۱۳/۱۱۳**؛ API **۴۳۵ پاس، ۱۱ کنارگذاشته‌شده، ۶۴ مجموعهٔ موفق**؛ Playwright **۸۱ + ۵ + ۲ = ۸۸ پاس**؛ آزمون‌های مستقل PostgreSQL و ساخت/آزمون Compose نیز سبز شدند. جزئیات در [گزارش آزمون](TEST_REPORT.md).

در CI، حساب مالکِ مصنوعی چهار کارت تنظیمات، Nexus و Manage Pulse، منوی پذیرش و ترخیص و صفحه‌های امداد ویژه در عرض موبایل را بررسی کرد. **بررسی تصویری Production با نشست واقعی مالک اجرا نشد:** هر دو ابزار مرورگر/رایانه با خطای زیرساختی `failed to write kernel assets` باز نشدند؛ راه‌اندازی مجدد ابزار هم ناموفق بود. بنابراین نمایش نسخه در بالای صفحه، چهار کارت، Nexus، قیف مشتری/قطعه و نام کوتاه/پلاک کامل با نشست واقعی مالک هنوز نیاز به بازبینی دارند؛ نتایج CI جای این بررسی زنده معرفی نمی‌شوند.

قدم بعد: بازبینی همین صفحه‌ها با نشست مالک؛ سپس مالک خودش اطلاعات کسب‌وکار را در Manage Nexus وارد کند و بررسی‌های نخستین اتصال را طبق [راهنمای پالس](MANAGE_PULSE_FA.md) انجام دهد. گزارش امداد ویژه و لیست نوبت همچنان دستی‌اند.
