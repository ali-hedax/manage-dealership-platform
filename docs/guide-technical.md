# راهنمای فنی منیج — برای مسئول آی‌تی نمایندگی

این سند توضیح می‌دهد منیج (Manage by HEDAX) با چه فناوری‌هایی ساخته شده، روی چه سروری اجرا می‌شود، داده از کجا می‌آید و به کجا می‌رود، نسخه‌ها چطور منتشر و برگردانده می‌شوند، از داده چطور پشتیبان گرفته می‌شود و دسترسی‌ها و امنیت چطور کنترل می‌شوند.

- **وضعیت متن:** آذر ۱۴۰۵ (۲۰۲۶-۱۱-۲۷). اگر این سند با [سند جامع مصوب](PRODUCT_SPEC_FA.md) فرق داشت، سند جامع درست است.
- **چه چیزی در این سند نیست:** هیچ رمز، توکن، کلید، نشانی IP یا مسیر داخلی سرور در این سند نیامده است. مخزن کد **عمومی** است. این اطلاعات فقط نزد مالک است و در گیت‌هاب، Issue، PR یا تصویر صفحه نوشته نمی‌شود.

## خلاصه در یک نگاه

- منیج یک **سامانهٔ تحت وب** است. کارکنان با مرورگر کامپیوتر یا گوشی وارد می‌شوند. روی دستگاه‌ها نرم‌افزاری نصب نمی‌شود (نصب روی صفحهٔ گوشی اختیاری است).
- سرور اصلی یک **ماشین مجازی در ابر آروان، داخل ایران** است. منیج روی سرورهای نمایندگی نصب نیست.
- داده‌های پذیرش از سامانهٔ **کسب‌وکار** ایساکو، با حساب خود نمایندگی و **فقط به‌صورت خواندنی**، می‌آیند. منیج در کسب‌وکار چیزی ثبت، ویرایش یا حذف نمی‌کند.
- هر نسخهٔ تازه فقط با **تأیید مالک** منتشر می‌شود. پیش از انتشار پشتیبان گرفته می‌شود و راه بازگشت آماده است.
- منیج فعلاً **آنلاین** است. اگر اینترنت نمایندگی قطع شود، منیج در دسترس نیست. حالت آفلاین روی سرور داخلی طراحی شده ولی هنوز ساخته و آزموده نشده است ([OFFLINE_SYNC](OFFLINE_SYNC.md)).

## ۱. فناوری‌ها

| بخش | فناوری | توضیح ساده |
| --- | --- | --- |
| زبان برنامه | TypeScript 5.9 روی Node.js 22 | یک زبان برای هر دو طرف (صفحه‌ها و سرور) |
| صفحه‌های وب | Next.js 16 و React 19 | فارسی و راست‌به‌چپ، با قلم وزیرمتن روی خود سرور (به گوگل وصل نمی‌شود). روی گوشی قابل نصب است (PWA) |
| سرور برنامه (API) | NestJS 11 | همهٔ قواعد کاری و کنترل دسترسی این‌جا اجرا می‌شود |
| دسترسی به پایگاه داده | Drizzle ORM 0.45 و SQL | تغییرات ساختار پایگاه داده (migration) فایل SQL شماره‌دار دارند |
| بررسی ورودی‌ها | Zod 4 | هر دادهٔ ورودی پیش از استفاده بررسی می‌شود |
| پایگاه داده | PostgreSQL 16 | تنها محل نگهداری داده. برای توسعه و آزمون یک نسخهٔ درون‌برنامه‌ای (PGlite) هم هست که در Production پذیرفته نمی‌شود |
| کانتینر | Docker و Docker Compose | هر بخش یک کانتینر جدا دارد (ایمیج‌های پایهٔ `node:22-alpine` و `postgres:16-alpine`) |
| وب‌سرور | Caddy | HTTPS و رساندن درخواست‌ها به برنامه. Nginx یا certbot روی سرور نیست |
| درگاه ورود (gate) | یک سرویس کوچک Node.js | پیش از هر صفحهٔ خصوصی بررسی می‌کند که کاربر واقعاً وارد شده باشد |
| لبهٔ شبکه | پراکسی ابر آروان | درخواست کاربران اول به آروان می‌رسد و آروان آن را به سرور می‌دهد |
| ثبت رخداد (لاگ) | pino (JSON) | رمزها، کوکی‌ها و سرآیندهای ورود در لاگ پوشانده می‌شوند |
| آزمون | Jest (سرور)، Playwright (مرورگر) | آزمون‌ها روی دادهٔ ساختگی اجرا می‌شوند |
| یکپارچه‌سازی پیوسته (CI) | GitHub Actions | در هر تغییر شش بررسی خودکار اجرا می‌شود (بخش ۴) |
| مدیریت بسته‌ها | pnpm 10 (monorepo) | سه بخش: `apps/web`، `apps/api` و `packages/shared` (قواعد مشترک و دسترسی‌ها) |
| اسکریپت‌های عملیات | Bash و Python | نصب، پشتیبان و بررسی سلامت روی سرور |

## ۲. معماری سرور اصلی

```
 کارکنان (مرورگر کامپیوتر / گوشی)
        │  HTTPS
        ▼
 پراکسی ابر آروان  ── گواهی لبه را خود آروان تمدید می‌کند
        │  HTTPS
        ▼
 ┌──────────────────── ماشین مجازی منیج (آروان، داخل ایران) ────────────────────┐
 │  Caddy   ← تنها سرویسی که پورت باز دارد (۸۰ و ۴۴۳)                             │
 │    ▼                                                                          │
 │  gate    ← بدون ورود معتبر، صفحهٔ خصوصی باز نمی‌شود                            │
 │    ▼                                                                          │
 │  web     ← صفحه‌ها (Next.js)؛ درخواست‌های /api را به API می‌دهد                │
 │    ▼                                                                          │
 │  api     ← قواعد کاری، دسترسی، ممیزی (NestJS)                                  │
 │    ▼                                                                          │
 │  db      ← PostgreSQL 16 (فقط داخل شبکهٔ کانتینرها)                           │
 │    ▲                                                                          │
 │  pulse   ← کارگر جدای «منیج پالس»؛ فقط اتصال خروجی به کسب‌وکار               │
 └───────────────────────────────────────────────────────────────────────────────┘
```

- **یک برنامه، یک پایگاه داده.** منیج میکروسرویس ندارد. API یک برنامهٔ واحد با بخش‌های جدا (پرونده‌ها، قطعات، امداد ویژه، پذیرش، گزارش‌ها و …) است.
- **فقط Caddy از بیرون دیده می‌شود.** API، پایگاه داده و پالس پورت عمومی ندارند. ورود SSH به سرور فقط با کلید است و رمز پذیرفته نمی‌شود.
- **پالس جداست.** پالس همان ایمیج API است ولی در فرایند جدا اجرا می‌شود و پورت ندارد. اگر پالس خطا بدهد، صفحه‌ها و API از کار نمی‌افتند. قفل پایگاه داده نمی‌گذارد دو پالس هم‌زمان کار کنند.
- **ساعت‌ها:** همهٔ زمان‌ها در پایگاه داده UTC ذخیره می‌شوند و در صفحه به تاریخ شمسی و وقت تهران نشان داده می‌شوند.
- **اینترنت سرور:** سرور به اینترنت بین‌الملل دسترسی ندارد (اندازه‌گیری آبان ۱۴۰۵). به همین دلیل ایمیج‌ها روی سرور ساخته نمی‌شوند: در CI ساخته و آزموده می‌شوند و همان فایل آزموده به سرور منتقل می‌شود. ایمیل دعوت هم از سرور فرستاده نمی‌شود و دعوت با لینک خصوصی انجام می‌شود.
- **گواهی HTTPS:** دو گواهی در کار است.
  - **گواهی لبه:** بین کاربر و آروان. خود آروان آن را تمدید می‌کند.
  - **گواهی مبدأ:** بین آروان و سرور. تا **۱۴ بهمن ۱۴۰۵ (۲۰۲۷-۰۲-۰۳)** اعتبار دارد و طبق تصمیم مالک خودکار تمدید نمی‌شود. پیش از این تاریخ باید جایگزین آن تعیین شود. جزئیات: [DEPLOYMENT](DEPLOYMENT.md#production-domain-and-certificate).
- **جدایی از Source by HEDAX:** Source پروژهٔ دیگری است. منیج سرور، پایگاه داده، کلید یا تنظیمات دامنه را با آن شریک نیست.

### محیط آزمایشی (staging)

بازسازی منیج روی شاخهٔ جدای `rebuild` ساخته می‌شود و هر نسخهٔ آن اول روی **محیط آزمایشی** نصب می‌شود. منیج اصلی تا جایگزینی نهایی دست نمی‌خورد.

محیط آزمایشی روی **همان ماشین مجازی** است، ولی هیچ بخشی از منیج اصلی را با آن شریک نیست:

| مورد | منیج اصلی | محیط آزمایشی |
| --- | --- | --- |
| نشانی | دامنهٔ اصلی | زیردامنهٔ جدا، پشت رمز جدای مرورگر |
| پایگاه داده | پایگاه دادهٔ اصلی | پایگاه دادهٔ جدا با فضای ذخیرهٔ جدا |
| ایمیج‌ها | برچسب ثابت هر نسخه | مخزن ایمیج جدا با نام دیگر |
| فایل تنظیمات و رمزها | فایل اصلی | پوشهٔ رمزهای جدا |
| داده | واقعی | نمونه، به‌علاوهٔ پذیرش‌هایی که پالس می‌خواند |
| حافظه | — | سقف حدود ۱٫۳ گیگابایت برای همهٔ سرویس‌های آن |

- **فقط صفحه‌های محیط آزمایشی** به شبکهٔ منیج اصلی وصل‌اند، تا Caddy بتواند درخواست را به آن‌ها برساند. این سرویس رمز پایگاه داده ندارد.
- **نصب در محیط آزمایشی هیچ برچسب ایمیجی از منیج اصلی را عوض نمی‌کند.** اگر هم‌پوشانی پیدا شود، نصب رد می‌شود. اگر برچسبی جابه‌جا شود، فوراً برگردانده می‌شود و نصب شکست می‌خورد.
- **پالس در محیط آزمایشی** فقط خواندنی است و دست‌کم هر ۳۰ دقیقه یک بار می‌خواند.

جزئیات: سند `docs/STAGING_FA.md` در شاخهٔ `rebuild`.

## ۳. جریان داده: از کسب‌وکار تا منیج تا نمایشگرها

```
 کسب‌وکار ایساکو ──(پالس، فقط خواندن)──►  پایگاه دادهٔ منیج  ──►  میز کار هر نقش
        │                                     ▲                       │
        └── فایل گزارش (دستی یا با پالس) ──────┘                       ├──► خروجی Excel و PDF، لیست شب
            پیش‌نمایش ← تأیید ← ثبت                                     └──► نمایشگرها (در دست ساخت)
```

### گام ۱: کسب‌وکار ← منیج (منیج پالس)

- پالس با **حساب خود نمایندگی** به کسب‌وکار وارد می‌شود. کد نمایندگی، نام کاربری و کلمهٔ عبور را مالک یا مدیر سیستم در «تنظیمات ← Manage Nexus» وارد می‌کند.
- **فقط خواندنی:** پالس یک فهرست ثابت از درخواست‌های مجاز دارد و هر درخواست دیگری را پیش از ارسال رد می‌کند.
- **کلمهٔ عبور کسب‌وکار** رمزگذاری‌شده در پایگاه داده نگه داشته می‌شود و هرگز به مرورگر برنمی‌گردد. در لاگ، خطا یا گزارش هم نمی‌آید.
- **حفاظت از حساب:** پس از دو ورود ناموفق پشت سر هم، پالس می‌ایستد و به مالک و مدیر سیستم اعلان می‌دهد. پالس هرگز پشت سر هم تلاش ورود نمی‌کند. اگر کسب‌وکار کد امنیتی (کپچا) یا تغییر رمز بخواهد هم پالس می‌ایستد.
- **فاصلهٔ خواندن (در ساعات کار):**

  | داده | هر چند وقت |
  | --- | --- |
  | پذیرش‌های امروز | هر ۳ دقیقه (قابل تنظیم، حداقل ۲) |
  | پذیرش‌های باز (۶۰ روز اخیر) | هر ۱۵ دقیقه |
  | قطعه، اجرت و ایراد کارت تازه یا تغییرکرده | فوراً |
  | کارت‌های باز امروز / قدیمی‌تر | هر ۱۰ / ۳۰ دقیقه |
  | موجودی انبار، گزارش امداد ویژه، لیست نوبت پذیرش | روزی یک بار، از حدود ساعت ۱۰ |

- **قاعدهٔ ثبت:** خواندن دوبارهٔ همان داده چیز تازه‌ای نمی‌سازد. هیچ ردیفی پاک نمی‌شود: قلمی که در کسب‌وکار نیست فقط علامت «حذف‌شده در کسب‌وکار» می‌گیرد. تنها استثنا گزارش اجراهای پالس است که پس از ۳۰ روز پاک می‌شود.

راهنمای کامل: [MANAGE_PULSE_FA](MANAGE_PULSE_FA.md).

### گام ۲: فایل‌های گزارش (Manage Nexus)

- همهٔ ورود دادهٔ کسب‌وکار از یک جا انجام می‌شود: **Manage Nexus**. نمونه‌ها: موجودی انبار، گزارش امداد ویژه، لیست نوبت پذیرش و گزارش توقف خودرو.
- هر فایل، چه پالس آن را بیاورد چه کسی دستی بارگذاری کند، از یک مسیر می‌گذرد: **پیش‌نمایش ← تأیید ← ثبت**. فایل تکراری دوباره ثبت نمی‌شود.
- پالس می‌تواند فایل‌هایی را که خوانده خودکار ثبت کند. ولی اگر فایل مشکوک باشد، برای تأیید یک نفر نگه داشته می‌شود. نمونه‌ها: ستون‌ها عوض شده‌اند، بخش بزرگی از کالاها در فایل موجودی نیست، یا ردیف‌های خطا زیاد است.
- ثبت گزارش‌های حجیم در پس‌زمینه انجام می‌شود و ممکن است چند دقیقه طول بکشد. بستن مرورگر کار را لغو نمی‌کند. اگر ثبت شکست بخورد، داده‌های قبلی دست نمی‌خورد.

### گام ۳: کار کارکنان در منیج

- هر نقش میز کار خودش را می‌بیند (بخش ۶).
- **هر تغییر در یک تراکنش ثبت می‌شود.** همراه تغییر یک ردیف ممیزی هم نوشته می‌شود: چه کسی، کی، چه چیزی را از چه به چه تغییر داد. ردیف ممیزی پاک‌شدنی یا ویرایش‌شدنی نیست (بخش ۷).
- **تأیید رسمی** (کارت طلایی، بیمه) فقط در سامانهٔ رسمی معتبر است. منیج آن را ثبت می‌کند و جای آن را نمی‌گیرد.

### گام ۴: خروجی‌ها و نمایشگرها

- **امروز در دسترس:** صفحه‌های هر نقش، خروجی Excel و PDF، لیست شب و اتاق کنترل مدیر خدمات.
- **نمایشگرها (تلویزیون) هنوز عملیاتی نیستند.** طرح ظاهری آن‌ها تأیید شده و فقط در محیط آزمایشی دیده می‌شود. در Production صفحهٔ پیش‌نمایش طرح بسته است. طبق [برنامهٔ تکه‌ها](manage-reconstruction/Manage-Slices.md) سه نمایشگر ساخته می‌شود:

  | نمایشگر | چه نشان می‌دهد |
  | --- | --- |
  | تابلوی سالن | خودروی فعلی هر جایگاه، صف، خودروهای منتظر جابه‌جایی |
  | تلویزیون سالن انتظار مشتری | پلاک با بخش پوشیده، نام کوتاه خودرو، مرحله و زمان تقریبی باقی‌مانده. **بدون نام مشتری** |
  | حالت تلویزیون دیدبان | نمای کلی مدیر، با چرخش خودکار |

- **طرح دسترسی نمایشگرها:** هر نمایشگر با یک **لینک قابل ابطال** باز می‌شود و فقط می‌تواند ببیند، نه تغییر بدهد. اگر لینک لو برود، ابطال می‌شود.
- **کار آی‌تی پس از ساخت نمایشگرها:**
  - یک تلویزیون یا مینی‌پی‌سی با مرورگر به‌روز و اینترنت پایدار
  - حالت تمام‌صفحه (kiosk)
  - خاموش کردن حالت خواب صفحه
  - قفل کردن دستگاه تا کسی به مرورگر آن دسترسی نداشته باشد

## ۴. نسخه‌بندی و بازگشت به نسخهٔ قبل

### کد و شاخه‌ها

- **مخزن:** کد در گیت‌هاب است. هر تغییر روی یک شاخهٔ جدا ساخته می‌شود و با یک درخواست ادغام (PR) بررسی می‌شود.
- **CI:** باید سبز باشد. ادغام در `main` و انتشار در Production فقط با تأیید صریح مالک انجام می‌شود. انتشار خودکار در Production وجود ندارد.
- **شاخهٔ `rebuild`:** کارهای بازسازی در این شاخه ادغام می‌شوند و نسخهٔ تازه خودکار روی محیط آزمایشی نصب می‌شود.

### شش بررسی CI در هر تغییر

| بررسی | چه چیزی را می‌سنجد |
| --- | --- |
| اسناد | پیوندهای اسناد و فهرست مسیرهای API |
| کد | lint، بررسی نوع، ساخت، آزمون‌های واحد و یکپارچه |
| PostgreSQL | اجرای migrationها روی PostgreSQL 16 واقعی، قفل‌ها، دست‌نخوردنی بودن ممیزی |
| مرورگر | آزمون سرتاسری با Playwright و تصویر صفحه‌ها |
| Docker | ساخت ایمیج‌ها، بالا آوردن کامل سامانه با دادهٔ ساختگی، آزمون درگاه HTTPS و رمز |
| امنیت | آسیب‌پذیری بسته‌ها، بازبینی وابستگی‌ها، جست‌وجوی رمز جاافتاده در کد (gitleaks) |

### شمارهٔ نسخه

- **قالب:** نسخه‌ها شماره‌ای مثل `v1.0.20` دارند. نسخهٔ در حال اجرا در زمان نگارش همین `v1.0.20` است.
- **زمان گرفتن شماره:** شماره **فقط پس از** گذشتن بررسی سلامت به یک commit داده می‌شود.
  - تأیید دوبارهٔ همان commit همان شماره را برمی‌گرداند.
  - انتشار ناموفقی که پیش از تأیید برگردانده شود شماره نمی‌گیرد.
  - بازگشت به نسخهٔ قدیمی همان شمارهٔ قدیمی را نشان می‌دهد.
- **اطلاع به کاربران:** پس از هر نسخه، چند خط کوتاه دربارهٔ تغییرات به کاربران نشان داده می‌شود. فهرست کامل تغییرات همهٔ نسخه‌ها در صفحهٔ «نسخه‌ها» (`/releases`) است.

### روند انتشار در Production

1. **تأیید مالک** همراه با شناسهٔ دقیق commit.
2. **CI سبز** روی همان commit. همان ایمیج‌هایی که CI ساخته و آزموده با بررسی checksum به سرور منتقل می‌شوند. روی سرور چیزی ساخته نمی‌شود.
3. **پشتیبان پیش از نصب** رمزگذاری‌شده، و بازیابی آزمایشی آن در یک پایگاه دادهٔ جدا.
4. **تمرین migration:** اگر نسخه migration دارد، روی نسخهٔ بازیابی‌شده تمرین می‌شود: اجرا، برگشت، اجرای دوباره. در هر مرحله ثابت می‌شود که ردیف‌های موجود تغییر نکرده‌اند.
   - migrationها **افزایشی** نوشته می‌شوند: ستون یا جدول تازه اضافه می‌کنند و داده‌ای پاک نمی‌کنند.
   - migration فقط **بیرون از ساعت کاری** (پس از ۱۹:۳۰ و پیش از ۰۷:۳۰ تهران) اجرا می‌شود.
   - Production هنگام روشن شدن خودکار migration اجرا نمی‌کند. migration یک گام صریح در اسکریپت انتشار است.
5. **قفل ایمیج:** Production هرگز ایمیج «آخرین» (`latest`) را اجرا نمی‌کند. هر نسخه برچسب ثابت خودش را دارد (`prod-<نسخه>`) و فایل تنظیم سرویس‌ها همان برچسب را نام می‌برد.
6. **جابه‌جایی:** معمولاً حدود ۱۰ تا ۴۵ ثانیه.
7. **بررسی سلامت:** API باید «سالم»، پایگاه داده «سالم» و commit در حال اجرا برابر commit مورد انتظار باشد. سپس شمارهٔ نسخه داده می‌شود. اگر commit جور نباشد، اسکریپت انتشار خودکار برمی‌گرداند.
8. **آزمون دود** روی یک نسخهٔ دورریختنی از پایگاه داده (ورود، صفحه‌های اصلی). پایگاه دادهٔ زنده در این آزمون دست نمی‌خورد.
9. **پشتیبان‌های نهایی** پس از نصب و ثبت گزارش انتشار در اسناد.

دستور کامل: [DEPLOYMENT](DEPLOYMENT.md).

### بازگشت به نسخهٔ قبل

- **بازگشت کد (راه معمول):** ایمیج‌های نسخهٔ قبل با یک برچسب بازگشت روی سرور نگه داشته می‌شوند. بازگشت یعنی برگرداندن برچسب در فایل تنظیم و بالا آوردن دوبارهٔ سرویس‌ها. چون migrationها افزایشی‌اند، کد قدیمی ستون‌ها و جدول‌های تازه را نادیده می‌گیرد و داده از دست نمی‌رود.
- **بازگشت داده (فقط اگر داده آسیب دیده باشد):** API و صفحه‌ها متوقف می‌شوند. از وضع آسیب‌دیده هم یک نسخه برای بررسی گرفته می‌شود. پشتیبان پیش از نصب در یک پایگاه دادهٔ تازه بازیابی، بررسی و سپس جایگزین می‌شود. اسکریپت‌های برگشت migration فقط برای پایگاه دادهٔ دورریختنی است، نه دادهٔ واقعی.
- **محیط آزمایشی:** یک فرمان نسخهٔ قبلی آن را دوباره بالا می‌آورد.
- **دسترسی‌ها پس از بازگشت:** بازگشت به نسخه‌ای که تنظیمات تازهٔ دسترسی را نمی‌شناسد ممکن است دسترسی‌های قدیمی را دوباره فعال کند. چنین بازگشتی پیش از اجرا بررسی امنیتی می‌خواهد. معمولاً اصلاح نسخهٔ جاری بهتر است.

## ۵. پشتیبان‌گیری

| نوع | کی | چه چیزی | کجا |
| --- | --- | --- | --- |
| روزانه | خودکار، هر روز ساعت ۰۴:۰۰ تهران | خروجی کامل پایگاه داده، فایل تنظیمات و رمزهای سرور، تنظیمات Caddy و گواهی، شناسهٔ commit و ایمیج‌های در حال اجرا، و checksum (SHA-256) همه | روی خود سرور، با دسترسی خصوصی |
| انتشار | هر انتشار: پیش از نصب، پایان نصب و پس از نصب | همان موارد، **رمزگذاری‌شده** | روی سرور |
| بیرون از سرور | پس از انتشارها، دستی | نسخهٔ رمزگذاری‌شده از پشتیبان‌های انتشار و کلیدهای لازم برای بازیابی | روی رایانهٔ مالک (رمزگذاری با حساب ویندوز او) |

- **هر پشتیبان انتشار آزموده می‌شود.** پشتیبان در یک پایگاه دادهٔ جدا بازیابی می‌شود و اثر انگشت همهٔ جدول‌ها با پایگاه زنده مقایسه می‌شود. سپس پایگاه موقت پاک می‌شود. پشتیبانی که بازیابی‌اش آزموده نشده، پشتیبان حساب نمی‌شود.
- **هیچ‌وقت مستقیم روی Production بازیابی نکنید.** همیشه اول در یک پایگاه دادهٔ جدا. دستورها: [BACKUP_RESTORE](BACKUP_RESTORE.md).
- **دو کلید سرور باید همراه پشتیبان بمانند.** این کلیدها در خود پشتیبان هستند و نسخهٔ امن آن‌ها نزد مالک است:
  - کلید ورود (`AUTH_TOKEN_SECRET`). بدون آن، Google Authenticator همهٔ مدیران باید از نو وصل شود.
  - کلید پالس (`PULSE_SECRET_KEY`). بدون آن، کلمهٔ عبور کسب‌وکار باید دوباره در تنظیمات وارد شود. داده‌های دیگر از بین نمی‌روند.
- **کارهای باز که آی‌تی می‌تواند در آن کمک کند:**
  - **پاک‌سازی:** پشتیبان روزانه عمداً هیچ نسخهٔ قدیمی را خودکار پاک نمی‌کند و فضای دیسک دستی پایش می‌شود. پیشنهاد سند پشتیبان: ۷ نسخهٔ روزانه و ۴ نسخهٔ هفتگی.
  - **انتقال بیرون از سرور:** انتقال خودکار روزانه به بیرون از سرور هنوز ساخته نشده و فقط نسخه‌های انتشار دستی منتقل می‌شوند. داشتن یک نسخه در محل یا ارائه‌دهندهٔ دیگر لازم است.

## ۶. نقش‌ها و دسترسی

### نقش‌ها و نحوهٔ ورود

صفحهٔ ورود دو در دارد: **ورود کارکنان** (نام کاربری و پین ۴ رقمی) و **ورود مدیر سیستم** (ایمیل، رمز و کد Google Authenticator). مالک از همان در مدیر سیستم وارد می‌شود.

| نقش | کار اصلی | ورود | نام کاربری |
| --- | --- | --- | --- |
| کارشناس تصادفات | پذیرش، کارشناسی، برنامهٔ تعمیر، کنترل نهایی، تحویل | پین | `EXP` + دو رقم |
| مسئول قطعات | تعیین تکلیف قطعه، رزرو، خرید، قیمت | پین | — |
| تکنسین جایگاه | شروع و پایان کار، «قطعه ندارم»، با گوشی | پین | `TECH` + کد جایگاه |
| مدیر خدمات | فقط دیدن، تحلیل و تذکر؛ کار عملیاتی ندارد | پین | `MGR` + دو رقم |
| اپراتور امداد ویژه و کارشناس پیگیری تأمین | میزهای امداد ویژه (کنار هر نقش دیگر) | پین | — |
| مهمان | فقط مشاهده با اطلاعات پوشیده و تاریخ پایان دسترسی | پین | `GST` + دو رقم |
| مدیر سیستم | رفع گره و ایراد، تنظیمات، بارگذاری گزارش، دعوت کارکنان اگر مالک اجازه داده باشد | دومرحله‌ای | — |
| مالک | همهٔ دسترسی‌ها و کارهای حساس | دومرحله‌ای | — |

### قواعد دسترسی

- **سمت با مجوز فرق دارد.** سمت (مثل سرپرست، پذیرشگر یا انباردار) فقط عنوان شغلی است و مجوزی نمی‌دهد.
- **نحوهٔ محاسبهٔ مجوزها:** مجوزهای نهایی هر نفر = مجوزهای الگوی نقش‌هایش، به‌علاوهٔ مجوزهای اضافهٔ شخصی، منهای ممنوعیت‌های شخصی.
- **چه کسی دسترسی‌ها را تغییر می‌دهد:** فقط مالک می‌تواند تک‌تک مجوزها یا الگوی نقش‌ها را تغییر دهد. هر تغییر دسترسی در ممیزی ثبت می‌شود.
- **کنترل روی سرور است.** پنهان شدن یک منو فقط ظاهری است. API در هر درخواست مجوز را دوباره بررسی می‌کند.
- **پین:**
  - ۵ پین اشتباه حساب را ۱۵ دقیقه قفل می‌کند.
  - حسابی که نقشی جز نقش‌های پین‌دار داشته باشد، هرگز با پین وارد نمی‌شود.
  - تنظیمات اتصال کسب‌وکار در نشست پین هرگز در دسترس نیست.
- **مهمان:** نام کامل مشتری، شاسی کامل، تلفن و مبالغ **روی سرور** پوشیده می‌شوند، نه فقط در ظاهر صفحه. مهمان فایل دریافت نمی‌کند. پس از تاریخ پایان، ورود و نشست مهمان قطع می‌شود.
- **بازیابی دسترسی کارکنان:**
  - مالک هویت همکار را حضوری یا تلفنی تأیید می‌کند و یک لینک بازیابی می‌سازد. لینک یک‌بارمصرف است و یک ساعت اعتبار دارد.
  - با پایان بازیابی، همهٔ نشست‌های قبلی آن نفر بسته می‌شود.
  - راه بازیابی حساب خود مالک هنوز تعیین نشده است.

جزئیات: [WORKSPACES_ACCESS_FA](WORKSPACES_ACCESS_FA.md)، [PERSONAL_AUTH_FA](PERSONAL_AUTH_FA.md)، [STAFF_IDENTIFIERS_FA](STAFF_IDENTIFIERS_FA.md).

## ۷. امنیت

| موضوع | چه کاری انجام می‌شود |
| --- | --- |
| رمزگذاری مسیر | HTTPS از کاربر تا آروان و از آروان تا سرور |
| سطح در معرض | فقط پورت‌های ۸۰ و ۴۴۳ باز است. ورود SSH فقط با کلید است |
| درگاه ورود | صفحهٔ خصوصی فقط با نشستی که با پین یا کد Authenticator تأیید شده باشد باز می‌شود. نشستی که فقط رمز زده و کد را نزده، بیرون می‌ماند |
| نشست | توکن تصادفی ۲۵۶ بیتی در کوکی httpOnly و Secure. در پایگاه داده فقط هش آن ذخیره می‌شود. اعتبار ۱۲ ساعت، با هر استفاده تمدید. خروج آن را باطل می‌کند |
| رمزها | رمز با scrypt هش می‌شود. کلید Authenticator و کلمهٔ عبور کسب‌وکار با AES-256-GCM رمزگذاری می‌شوند |
| حملهٔ حدس رمز | ۵ ورود ناموفق: ۱۵ دقیقه قفل. حداکثر ۱۰ درخواست ورود و ۶۰۰ درخواست در دقیقه برای هر IP |
| تشخیص IP واقعی کاربر | Caddy فقط به محدوده‌های رسمی IP آروان اعتماد می‌کند. اگر آروان محدودهٔ تازه‌ای اضافه کند و در تنظیمات نباشد، کاربرانی که از آن می‌آیند یک سقف ورود مشترک پیدا می‌کنند. این فهرست باید گاه‌به‌گاه با فهرست رسمی آروان مقایسه شود |
| درخواست جعلی (CSRF) | هر درخواست تغییردهنده باید سرآیند ویژهٔ برنامه را داشته باشد. صفحه و API هم‌مبدأند |
| ورودی | هر ورودی با Zod بررسی می‌شود. پیام خطا فارسی است و جزئیات داخلی را نشان نمی‌دهد |
| ممیزی | جدول ممیزی با یک trigger در پایگاه داده **فقط افزودنی** است: ویرایش و حذف در آن ممکن نیست. ثبت می‌شود: انجام‌دهنده، زمان، دلیل، مقدار قبل و بعد، شناسهٔ درخواست و IP |
| لاگ | رمز، کوکی و سرآیند ورود در لاگ نمی‌آید |
| جداسازی داده | هر ردیف به نمایندگی خودش وابسته است و هر پرسش با نمایندگی کاربر فیلتر می‌شود |
| رمزهای سرور | رمزها در فایل تنظیمات روی سرور با دسترسی ۶۰۰ (فقط حساب سرویس منیج) نگه داشته می‌شوند و هرگز وارد گیت نمی‌شوند |
| زنجیرهٔ تأمین | در CI: بررسی آسیب‌پذیری بسته‌ها و جست‌وجوی رمز جاافتاده در کد. این بررسی در صورت پیدا کردن رمز، ادغام را متوقف می‌کند |
| موتورهای جست‌وجو | سرآیند `noindex`. سایت در نتایج جست‌وجو نمی‌آید |
| دسترسی ابزار خودکار | کلید ابزار توسعهٔ خودکار برای محیط آزمایشی فقط چند فرمان مشخص (وضعیت، لاگ، نصب، بازگشت، آزمون) را اجرا می‌کند و shell ندارد. هر فرمان روی سرور اصلی تأیید تک‌به‌تک مالک را می‌خواهد |

### کمبودهای شناخته‌شده

- حالت آفلاین و سرور داخلی نمایندگی هنوز ساخته نشده‌اند.
- انتقال خودکار پشتیبان به بیرون از سرور هنوز ساخته نشده است.
- راه بازیابی حساب مالک تعیین نشده است.
- گواهی مبدأ در ۱۴ بهمن ۱۴۰۵ منقضی می‌شود.

فهرست کامل: [SECURITY](../SECURITY.md).

## ۸. کار مسئول آی‌تی نمایندگی

**انجام دهید:**

- **دستگاه‌های کارکنان:** مرورگر به‌روز داشته باشند (Chrome، Edge یا Safari). ساعت و تاریخ دستگاه **خودکار** باشد، چون کد Google Authenticator با ساعت نادرست پذیرفته نمی‌شود.
- **نصب روی گوشی (اختیاری):** نشانی منیج را در مرورگر باز کنید و «نصب برنامه» یا «افزودن به صفحهٔ اصلی» را بزنید ([PWA_FA](PWA_FA.md)).
- **اینترنت:** پایداری اینترنت نمایندگی را پایش کنید. منیج بدون اینترنت در دسترس نیست.
- **قفل دستگاه:** دستگاه‌های مشترک (کامپیوتر پذیرش، و بعداً تلویزیون‌ها) قفل صفحه داشته باشند. کارکنان پس از کار از منیج خارج شوند.
- **گزارش مشکل:** مشکل را با زمان دقیق و نام صفحه به مالک یا مدیر سیستم گزارش دهید. نوشتن پیام خطا کمک می‌کند. تصویر صفحه با دادهٔ مشتری را در گروه‌های عمومی نفرستید.
- **سرور داخلی:** اگر قرار شد منیج روی سرور داخلی نمایندگی هم نصب شود، اول به [چک‌لیست سرور داخلی](IT_SERVER_CHECKLIST_FA.md) پاسخ دهید.

**انجام ندهید:**

- پین، رمز، کد Authenticator یا QR آن را برای کسی نفرستید. حتی برای پشتیبانی.
- فایروال، DNS، دامنه یا تنظیمات آروان را بدون تأیید مالک تغییر ندهید.
- اطلاعات واقعی مشتری، نشانی سرور یا رمز را در گیت‌هاب ننویسید. مخزن عمومی است.
- روی سرور منیج نرم‌افزار دیگری نصب نکنید و از آن برای پروژهٔ دیگری استفاده نکنید.
